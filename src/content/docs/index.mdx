**ee** brings structure to environment variables and secrets. Define a schema, keep your values in a Git repo, and let CI push them wherever they belong — GitHub Actions secrets, Cloudflare Workers, or a hydrated `.env` at deploy time.

## Keep your secrets in a Git repo

Give your team a private **secrets repo**: one folder per project, real values in `.env` sheets, and a small `.ee` file that says where each set of values belongs. Commit a change — CI syncs it everywhere.

<div class="grid grid-cols-1 lg:grid-cols-2 gap-8 items-start my-8">
  <div>

  ```text title="my-secrets/  ·  a private repo"
  projects/
  ├── api/
  │   ├── .ee              # where these values go
  │   ├── production.env   # the actual KEY=VALUE secrets
  │   └── staging.env
  ├── web/
  │   ├── .ee
  │   └── production.env
  └── worker/
      ├── .ee              # → a Cloudflare Worker
      └── production.env
  .github/workflows/
  └── sync-secrets.yml     # one action syncs it all
  ```

  </div>
  <div class="mt-2">

  - **`.env` sheets** hold the real values, versioned like any other file.
  - **`.ee`** carries no secrets — just the project name, its environments, and its origins (where to push).
  - **Push to `main`** and the sync action fans out over every project and pushes each one to GitHub or Cloudflare.
  - Review changes in a PR, roll back with `git revert`, and see exactly who changed what.

  </div>
</div>

## Sync everything with one action

Point the [**sync action**](/github-actions/#sync-action) at the repo and every project is pushed to its origins on each commit. That's the entire workflow:

```yaml title=".github/workflows/sync-secrets.yml"
on:
  push:
    branches: [main]
    paths: ["projects/**"]

jobs:
  sync:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: n1rna/ee-action/sync@v1
        with:
          gh_token: ${{ secrets.GH_PAT }}
          # cloudflare_api_token: ${{ secrets.CF_API_TOKEN }}   # if any CF origins
```

## Three actions, whichever fits

Reach for one action for a whole repo, one for a single environment, or read the secrets back in a consuming repo's CI — [full reference →](/github-actions/)

```yaml title="Sync — push every project in the repo"
- uses: n1rna/ee-action/sync@v1
  with:
    gh_token: ${{ secrets.GH_PAT }}
```

```yaml title="Push — one environment to one origin"
- uses: n1rna/ee-action/push@v1
  with:
    config_path: projects/api/.ee
    environment: production
    gh_token: ${{ secrets.GH_PAT }}
```

```yaml title="Hydrate — read a secret back into .env at deploy time"
- uses: n1rna/ee-action/hydrate@v1
  with:
    environment: production
    config_path: .ee
    env_file: .env.production
    gh_secret: ${{ secrets.ENV_PRODUCTION }}
```

## One `.ee` file ties it together

The `.ee` file is the whole configuration: the project, its environments (each pointing at value sheets), and its origins. No secrets live here — it's safe to commit anywhere.

```json title="projects/api/.ee"
{
  "project": "api",
  "environments": {
    "production": { "sheets": ["production.env"] },
    "staging": { "sheets": ["staging.env"] }
  },
  "origins": {
    "github": {
      "type": "github",
      "mode": "bundled",
      "secret_name": "ENV_PRODUCTION",
      "repo": "myorg/app",
      "environment": "production",
      "sync_env": "production"
    }
  }
}
```

In an application repo you can also add a `schema` block to validate variable names, types, and defaults — see [Project Configuration](/cli/project-configuration) and [Schemas](/cli/schemas).

## …or drive it from the CLI

Everything the actions do, you can do locally with the same tool:

```bash title="ee — from your machine"
# Preview what would be pushed (nothing is written)
ee push github production --dry-run

# Push one environment to its origin
ee push github production

# Run a command with the environment loaded
ee apply production -- npm start

# Materialize a .env file (schema defaults + resolved values)
ee hydrate production -o .env
```
